# MVP：把第一版缩成可验证的完整流程

## 使用时机与输入

产品定位大致清楚，需要决定第一版功能时使用。输入是已确认用户、主要场景、预算、开发期限和限制。如果核心用户仍不明确，先回到产品发现，不靠功能清单代替问题定义。

MVP 是能完成关键任务的最小可用版本，不是把每个模块做一半，也不是固定必须有若干个模块。

## 划分范围

1. 画出一次完整任务：进入 → 提交输入 → 处理 → 获取结果 → 保存或离开。
2. 对每一步列必须条件、业务规则、空状态、失败状态、恢复方法。
3. 将功能分为核心必需、核心依赖、后续增强、未来想法。只有缺了就无法验证核心价值的内容进入第一版。
4. 登录只有在需要隔离用户数据、跨设备保存、计费归属等情况下才加入；公开试用也要评估滥用成本。
5. 支付、管理后台、推荐系统、独立搜索、CDN、多个统计平台、内容自动化都需说明必要性，不因为别的产品有就照搬。
6. 明确本次不做内容及将来重新评估的触发条件。新想法进入 TODO，不打断当前已批准任务。

给候选任务标 P0/P1/P2：P0 是缺少就无法验证第一版核心价值的必需项；P1 是重要但可在核心流程后安排的事项；P2 是后续增强。优先级不能代替是否纳入当前版本的确认，每项另标本次做/以后做/暂不做。这里是开发排期含义；发布审计的 P0/P1/P2 按风险定义，不能因为任务原排 P2 就降低已发现漏洞的严重性。

## 页面、数据和流程需要一起确认

对每个页面记录用户、主要操作、输入输出、权限、加载/失败/空状态、手机体验。记录页面之间如何跳转，成功后去哪里，失败时是否丢失输入。

对每类数据说明来源、用途、归属、保存方式与期限。模拟数据只能用于演示，不能把假支付、假保存、假 AI 结果当作完整功能。

## 写出可检查的验收标准

按“给定前提 → 用户操作 → 可观察结果”表述。例如：已有一条本人笔记，修改并保存后刷新，仍显示新内容；无权限的用户不能读取这条笔记。

至少考虑正常路径、输入无效、依赖失败、重复点击、刷新/返回、手机布局。只在相关时增加离线、并发、登录过期等场景。

每项任务带目标、范围、前置条件、验收、验证方式和状态。状态可用待确认/待办/进行中/受阻/待验收/完成；“完成”须有实现和验证证据，不凭主观百分比。

## 和用户确认的内容

- 第一版要跑通哪一条用户任务，核心功能和页面有哪些。
- 暂不做什么，哪些依赖外部服务或额外费用。
- 需保存什么数据，是否有真实用户、权限、付费和敏感信息。
- 用什么场景和证据判定成功。
- 推荐一起做、以后做、暂不建议做的增强，分别说明成本。

范围和初步架构分别确认后，再初始化项目文档并编码。如果用户增加重大需求，说明对时间、成本、验收和技术方案的影响，给出缩小方案，不默默扩大范围。

验收：第一版可独立演示核心价值；没有未经同意的功能；每项核心任务有可观察标准；计划能落地到下一项小任务。
