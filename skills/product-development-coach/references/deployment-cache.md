# 部署、缓存、资源与性能

## 使用时机

选择托管平台或服务器、准备发布、遇到 504/内存不足、页面旧内容、图片带宽异常或推广前容量评估时使用。先定位具体环境，不能把朋友某次故障经验写成所有项目规则。

## 选择运行方式

按实际需求比较托管平台、容器或传统服务器：长驻进程、后台任务、任务时长、内存与磁盘持久性、数据库/搜索位置、目标地区、网络可达性、团队维护能力、备份和费用。

网站、数据库、搜索、爬虫同机部署可能简单，也会争抢资源；不能按少量请求就断言服务器足够。托管平台也不能仅凭品牌推断一定适合或不适合中国用户。节点、地区、价格、备案和业务限制使用时查官方资料，必要时真实测量。

## 先收证据

记录故障时间、URL、环境、版本、请求耗时、状态码、应用/代理日志、内存峰值、CPU、磁盘与连接数、重任务和依赖状态。504 只能说明某链路超时，不直接等于“内存不足”或“必须换平台”。

依次检查客户端 → CDN/代理 → 应用 → 数据库/搜索/外部 API；识别首次慢、每次慢、登录后慢、特定地区慢。先处理证实的瓶颈。

## 缓存设计

| 内容 | 先考虑 | 防止的问题 |
| --- | --- | --- |
| 带内容指纹的静态文件 | 长缓存与版本化 URL | 新旧资源不匹配 |
| 公开匿名页面 | 按内容更新频率设置 TTL/再验证 | 过期内容、缓存击穿 |
| 用户个人数据 | 私有缓存或不存储，按敏感性决定 | 跨用户泄漏 |
| 登录、订单、支付、会员接口 | 明确禁用共享缓存或严格隔离 | 错误余额、错误权限 |
| 查询/API 结果 | 参数、权限、语言和版本完整纳入键 | 不同条件共用同一结果 |
| 私密文件 | 鉴权和受控签名访问 | 缓存绕过访问控制 |

先画出浏览器、Service Worker（如有）、CDN、反向代理、框架页面/数据、应用和数据库缓存层。给每层记录键、TTL、失效触发、更新策略、负责人。`no-cache` 通常要求复用前再验证，不等于禁止存储；需不存储时核实 `no-store` 及实际链路行为。

缓存匿名内容前验证是否受 Cookie、Authorization、语言、查询参数影响；不能简单把全部页面改成 public。缓存私密信息是发布阻塞问题。

## 缓存不更新的定位步骤

1. 比较内容来源和版本，确认服务端实际数据已更新。
2. 读取响应头与内容，分别验证源站和 CDN；记录命中、Age、ETag 等可用证据。
3. 以干净会话或禁用浏览器缓存做对照；存在 Service Worker 时单独检查，不擅自卸载用户设置。
4. 检查框架的当前版本与缓存语义，核对失效路径/标签/数据键。
5. 提出针对已证实层级的最小更改，并验证更新后、缓存命中时及不同用户下结果。

不要盲目清全站 CDN、清数据库或重装项目。生产清缓存会增加回源流量，应先说明范围和影响，按授权执行。

## 推广和资源受限场景

建立应用与重任务资源预算；必要时限并发、排队、错峰、预生成公共内容。只有项目确实需要且批准时才暂停爬虫/批任务；记录任务名、停止命令、在途任务处理、恢复步骤和检查，不能只停不恢复。

升级机器只是候选之一，要同时核实进程峰值、泄漏、查询、渲染和缓存。公开压测、生产压测和可能产生费用的测试需明确授权与上限。

## 发布前后

发布前记录目标、版本、变更范围、环境变量名称、迁移兼容性、备份、后台任务、回滚和检查项。预览不等于上线授权。依赖数据库变更时不能假设回滚代码就能恢复数据。

发布后从外部访问确认域名/HTTPS、核心流程、错误率、日志和后台任务恢复，核对静态资源与缓存版本。失败按停止条件回退或请求处置；没执行远端检查不得声称线上正常。

交付 [OPERATIONS.md](../templates/OPERATIONS.md) 中的运行、缓存、任务和恢复说明，具体限制只写实际证据。HTTP 缓存语义参考 [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)，框架配置查对应版本官方文档。
