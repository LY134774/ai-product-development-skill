# 上线审计：先报告，再修复，再按授权发布

## 什么时候用

“产品准备上线”“上线前全面检查”“发布这个版本”时加载。能用就尽早验证市场，不等于跳过数据、支付和安全底线。范围锁定当前版本，避免审计变成无限加功能。

## 先记录发布对象

目标仓库/站点/环境、版本或提交、MVP 验收、用户群、变更范围、已批准操作。用户只要求检查时执行只读审计；用户明确批准修复的再逐项修；发布要有具体授权。

每项状态使用通过、问题、未验证、不适用；不适用需理由，未验证需原因与人工步骤。填写 [RELEASE_CHECKLIST.md](../templates/RELEASE_CHECKLIST.md)，不要默认全部打勾。

只核对环境变量的名称、存在性、环境归属和必要结构，不回显秘密值。无法检查的云设置、账号权限或外部状态列为未验证及人工确认事项。代码与文档矛盾时写出证据和需更新内容，不能把文档中的完成状态直接当作测试结果。

## 全面审计的专项加载顺序

先列项目实际组件与适用性，再按下表读取。此表只控制审计范围，不要求安装服务、增加产品功能或执行生产变更。

| 发现的条件 | 必须加载 | 本轮至少交付 |
| --- | --- | --- |
| 所有产品 | [开发与验证](implementation.md) | 核心任务、页面/交互或对应产品界面的真实验收，检查命令与结果 |
| 有部署、运行环境、文件或数据保存 | [部署与缓存](deployment-cache.md) | 组件适配、性能/资源、持久化、备份恢复与回滚证据 |
| 有账号、API、用户输入/上传、私有数据或高成本资源 | [安全与防刷](security-abuse.md) | 权限、输入、密钥、配额、并发、费用保护检查 |
| 有支付、订阅或额度权益 | [支付专项](payments.md) | 业务规则、可信定价、验签、幂等、权益、退款与相关自动化测试 |
| 需要公开搜索流量 | [SEO/GEO](seo-geo.md) | 公开边界、抓取/索引配置、内容质量、站长台账与未知外部状态 |
| 有统计采集或需要用数据验收 | [统计专项](analytics.md) | 事件、去重、真实流程核验、数据区域和待确认事项 |
| 准备向用户发布 | [运营与增长](operations-growth.md) 的监控、应急、第一周部分 | 运行与费用监控预案、故障应对、适用的第一周计划 |

每个适用专项记录已读指南、已检查项、证据和未检查原因；不适用的模块写明理由。不得省略未验证项后只汇总通过项。多个模块的相同问题合并成一条，保留关联证据。

## 审计清单

| 领域 | 核心检查 | 可接受证据 |
| --- | --- | --- |
| 需求 | 核心流程、错误恢复、范围、不做项 | 逐场景验收结果 |
| 页面 | 手机/桌面、加载/空/失败、表单、键盘、真实文案 | 预览操作或截图；说明没检查的设备 |
| 工程 | 依赖与锁文件、类型/Lint/相关测试/构建 | 实际命令、退出码与失败详情 |
| 数据 | 归属、保存、备份、恢复、迁移兼容和失败策略 | 测试记录与恢复演练；只“开备份”不够 |
| 登录权限 | 无登录、跨用户/租户、会话失效、管理操作 | 服务端权限测试 |
| API 与费用 | 限流、配额、并发、重试、上传与模型成本 | 受控测试及用量监控 |
| 密钥 | 前端/仓库/日志/历史、环境隔离、最小权限 | 扫描范围、结果与人工复核 |
| 支付（如有） | 定价、签名、幂等、订单/权益、退款续费 | 沙盒矩阵及正式环境待确认项 |
| 部署资源 | 运行时、常驻任务、CPU/内存/磁盘、超时 | 目标环境证据，不能只推测 |
| 缓存 | 更新失效、跨用户隔离、版本一致 | 匿名/登录/两用户对照与响应头 |
| SEO/GEO（如需） | 公开边界、状态、robots、Sitemap、元数据、多语言 | URL/配置检查、台账；不保证收录 |
| 统计（如需） | 事件、重复、转化来源、隐私和预算 | 一条实际流程与后台对账 |
| 运维 | 日志告警、健康检查、任务恢复、负责人 | 已配置与演练证据 |
| 法务与内容 | 隐私/条款/退款告知、版权、品牌与收集字段 | 用户确认和必要专业审核；不冒充认证 |
| 发布与回滚 | 可重现版本、数据库兼容、配置、回退、检查项 | 明确步骤与授权记录 |

只加载确实需要的专项指南进一步核查，不把所有检查变成强制安装新工具。扫描公共源代码前也要考虑向外部平台传输代码的授权。

## 关键场景的检查方法

| 适用条件 | 怎么检查 | 记录什么 |
| --- | --- | --- |
| 有用户界面 | 从入口完成核心任务，检查主要按钮/链接、表单、正常/空/错误状态；网站再检查 404/500、手机与桌面 | 页面或操作路径、实际结果、复现与未测设备 |
| 有保存/下载 | 提交后刷新或重新读取，核对结果与归属；验证失败是否错误提示成功 | 存储证据、权限、刷新后的结果，标明模拟保存 |
| 有账号 | 注册/登录/退出或项目实际认证流程、失效与跨用户访问 | 服务端权限和实际操作；未提供账号时标未验证 |
| 有数据库/文件 | 核对备份范围、迁移、连接与索引、恢复步骤；条件允许且获准时在测试环境恢复 | 备份与文件恢复结果；只存在备份配置不算恢复通过 |
| 有正式部署 | 核对域名、DNS、HTTPS、环境隔离、持久磁盘、资源和后台任务 | 本地/预览/生产分开记录，拿不到的远端状态列人工确认 |
| 涉及用户权益 | 检查可访问的隐私/服务条款、收集用途与保留、适用的 Cookie 告知、取消/退款入口、续费说明、AI/上传内容规则 | 与真实业务是否一致、待确认法律事项；不判定法律认证通过 |
| 面向受监管地区或部署节点 | 按业务、地区核实备案/许可及数据跨境等适用要求 | 当前权威来源、日期和需专业判断的部分，不内置固定法条结论 |
| 准备获取第一批用户 | 按市场评估反馈入口、Beta/Early Access、候补名单、演示/开源或相关渠道 | 给少量优先渠道及理由、执行前提，不默认全部制作或自动投递 |

检查目标是发现真实风险；某项缺失不自动等于必须新增功能。例如无收费业务时支付标不适用，单机 MVP 的单点故障可先明确恢复方案，不直接要求搭建集群。

## 问题分级

- 阻塞：已证实数据泄漏/越权、密钥暴露、不可逆数据风险、计费错误、核心流程不可用、无法控制高成本消耗等。先修复并验证。
- 高优先级：明显影响核心任务、恢复或运维，需在发布前确认解决或明确风险接受。
- 后续优化：不影响核心价值和底线的性能、文案、视觉或低收益扩展，进入 TODO。

每项写证据、影响、复现、建议、负责人、验证、状态。不能以数量或主观评分掩盖一个严重问题。发现只是假设时说明验证方法，不用高危标签制造恐慌。

报告使用 P0（阻塞）、P1（上线前优先）、P2（后续优化）表示优先级，TBD 表示证据或确认不足，不把未知当低风险。总体结论为 GO（当前范围具备发布条件）、CONDITIONAL GO（指定条件尚待满足）、NO-GO（存在阻塞）；关键权限、支付或恢复条件缺证据时写“暂无法判定”，不能用 GO 掩盖。任何结论都不等于用户已批准发布。

每个问题补充预估工作量和是否必须发布前完成；不确定的估算标明假设。运行未执行、执行失败、通过和需要人工检查的结果分别列出。

## 修复与授权

先给报告与最小修复批次，让用户选择；已明确授权当前修复范围时继续执行。新增功能、换平台、改支付方式、升级付费服务和生产数据库操作不能混在“审计通过”里自动做。

发布前说明位置、版本、影响范围、预计中断、后台任务、数据库/配置依赖、备份、回滚和发布后检查。模糊“可以/继续”不是线上确认；已给明确发布范围的授权不重复询问。

发布计划按实际产品分为准备期（可提前一天）、发布当天、发布后检查、第一周观察：准备期核实版本/备份/必要授权与负责人；当天核对环境和必要任务后执行获准步骤；发布后验核心流程、日志、缓存和任务恢复；第一周按运营指南调整观察重点。日期与动作根据规模简化，不为本地工具或小版本机械安排七天工作。

## 发布后验证

核对远端真实提交/Release 或目标部署版本；外部域名、HTTPS、核心用户任务、错误日志、资源、支付回调和任务恢复按适用范围检查。没有远端证据只报告“本地完成/已提交/部署请求已发出”等准确阶段。

发布失败记录发生在哪一步、是否部分生效、当前线上版本和恢复状态。不要反复点击发布、强推覆盖别人提交或删除历史来掩盖失败。

审计交付验收：适用性、证据、未验证项、问题与建议已完整报告，用户可以核对。发布就绪验收：已确认阻塞已解决并复验，关键检查没有悬而未决的未知，发布与回滚可执行；否则保留否定或待定结论。实际发布完成还必须有明确授权和远端结果。清单不等于安全认证，也不保证未来无故障。
