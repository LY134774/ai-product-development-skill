# 上线审计：先报告，再修复，再按授权发布

## 什么时候用

“产品准备上线”“上线前全面检查”“发布这个版本”时加载。能用就尽早验证市场，不等于跳过数据、支付和安全底线。范围锁定当前版本，避免审计变成无限加功能。

## 先记录发布对象

目标仓库/站点/环境、版本或提交、MVP 验收、用户群、变更范围、已批准操作。用户只要求检查时执行只读审计；用户明确批准修复的再逐项修；发布要有具体授权。

每项状态使用通过、问题、未验证、不适用；不适用需理由，未验证需原因与人工步骤。填写 [RELEASE_CHECKLIST.md](../templates/RELEASE_CHECKLIST.md)，不要默认全部打勾。

## 审计清单

| 领域 | 核心检查 | 可接受证据 |
| --- | --- | --- |
| 需求 | 核心流程、错误恢复、范围、不做项 | 逐场景验收结果 |
| 页面 | 手机/桌面、加载/空/失败、表单、键盘、真实文案 | 预览操作或截图；说明没检查的设备 |
| 工程 | 依赖与锁文件、类型/Lint/相关测试/构建 | 实际命令、退出码与失败详情 |
| 数据 | 归属、保存、备份、恢复、迁移兼容和失败策略 | 测试记录与恢复演练；只“开备份”不够 |
| 登录权限 | 无登录、跨用户/租户、会话失效、管理操作 | 服务端权限测试 |
| API 与费用 | 限流、配额、并发、重试、上传与模型成本 | 受控测试及用量监控 |
| 密钥 | 前端/仓库/日志/历史、环境隔离、最小权限 | 扫描范围、结果与人工复核 |
| 支付（如有） | 定价、签名、幂等、订单/权益、退款续费 | 沙盒矩阵及正式环境待确认项 |
| 部署资源 | 运行时、常驻任务、CPU/内存/磁盘、超时 | 目标环境证据，不能只推测 |
| 缓存 | 更新失效、跨用户隔离、版本一致 | 匿名/登录/两用户对照与响应头 |
| SEO/GEO（如需） | 公开边界、状态、robots、Sitemap、元数据、多语言 | URL/配置检查、台账；不保证收录 |
| 统计（如需） | 事件、重复、转化来源、隐私和预算 | 一条实际流程与后台对账 |
| 运维 | 日志告警、健康检查、任务恢复、负责人 | 已配置与演练证据 |
| 法务与内容 | 隐私/条款/退款告知、版权、品牌与收集字段 | 用户确认和必要专业审核；不冒充认证 |
| 发布与回滚 | 可重现版本、数据库兼容、配置、回退、检查项 | 明确步骤与授权记录 |

只加载确实需要的专项指南进一步核查，不把所有检查变成强制安装新工具。扫描公共源代码前也要考虑向外部平台传输代码的授权。

## 问题分级

- 阻塞：已证实数据泄漏/越权、密钥暴露、不可逆数据风险、计费错误、核心流程不可用、无法控制高成本消耗等。先修复并验证。
- 高优先级：明显影响核心任务、恢复或运维，需在发布前确认解决或明确风险接受。
- 后续优化：不影响核心价值和底线的性能、文案、视觉或低收益扩展，进入 TODO。

每项写证据、影响、复现、建议、负责人、验证、状态。不能以数量或主观评分掩盖一个严重问题。发现只是假设时说明验证方法，不用高危标签制造恐慌。

报告可对应为 P0（阻塞）、P1（上线前优先）、P2（后续优化）、TBD（证据或确认不足）。结论可用 GO（当前范围具备发布条件）、CONDITIONAL GO（指定条件尚待满足）、NO-GO（存在阻塞）；证据不足时明确写无法判定，不能用 GO 掩盖未验证项。任何结论都不等于用户已批准发布。

每个问题补充预估工作量和是否必须发布前完成；不确定的估算标明假设。运行未执行、执行失败、通过和需要人工检查的结果分别列出。

## 修复与授权

先给报告与最小修复批次，让用户选择；已明确授权当前修复范围时继续执行。新增功能、换平台、改支付方式、升级付费服务和生产数据库操作不能混在“审计通过”里自动做。

发布前说明位置、版本、影响范围、预计中断、后台任务、数据库/配置依赖、备份、回滚和发布后检查。模糊“可以/继续”不是线上确认；已给明确发布范围的授权不重复询问。

## 发布后验证

核对远端真实提交/Release 或目标部署版本；外部域名、HTTPS、核心用户任务、错误日志、资源、支付回调和任务恢复按适用范围检查。没有远端证据只报告“本地完成/已提交/部署请求已发出”等准确阶段。

发布失败记录发生在哪一步、是否部分生效、当前线上版本和恢复状态。不要反复点击发布、强推覆盖别人提交或删除历史来掩盖失败。

验收：所有阻塞解决或确切说明未解决；用户可以查看结果；发布与回滚可执行；正式发布结果有远端证据。清单不等于安全认证，也不保证未来无故障。
