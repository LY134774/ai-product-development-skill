# 项目文档、开发记忆与交接

## 使用时机

需求和初步架构已确认，需要初始化项目；开发中记录新想法和决策；上下文将满、换聊天/换模型或新 Agent 接手时使用。单纯讨论想法时不抢先创建一堆项目文件。

## 创建前先核对

确认项目根目录、已有文件、用户文件修改、当前分支和适用指令。先给出准备创建/更新的路径、原因、查看方法；同名文件先读后比较，未经确认不覆盖。不要执行全局 AGENTS.md 写入。

建议项目布局（沿用已有结构优先）：

```text
project/
  AGENTS.md
  README.md
  docs/
    TODO.md
    DECISIONS.md
    HANDOFF.md
    SEO_GEO.md             # 需要公开搜索流量时
    SEO_GEO_LEDGER.md      # 实际接入或审计时
    ANALYTICS.md           # 需要统计时
    RELEASE_CHECKLIST.md   # 准备发布时
    OPERATIONS.md          # 准备运行维护时
```

模板是可复用底稿，不是自动创建清单。未知字段写“待确认”，不能编造技术栈、部署地址、测试结果、完成比例或平台接入状态。

## 各文档各记什么

| 文档 | 应写 | 不应写 |
| --- | --- | --- |
| AGENTS.md | 当前项目已确认规则、命令、业务与运行约束 | 另一个产品的 2GB 限制、未经同意的固定技术栈 |
| README | 产品用途、当前能力、运行前提、真实命令、配置名称、查看方式 | 密钥原值、未实现功能宣传 |
| TODO | 有编号的任务、Bug、新想法、优先级、依赖、状态、验收 | 把所有想法默认塞进当前 MVP |
| DECISIONS | 唯一编号、日期、背景、备选、确认方案、原因、影响 | 未批准提案冒充最终决定 |
| HANDOFF | 代码核对后的当前状态、修改文件、验证、问题、下一项任务 | 聊天全文、仅凭记忆的“已完成” |
| SEO_GEO / 台账 | 策略与实际状态分别记录 | 提交 URL 等同收录、访问爬虫等同 AI 推荐 |
| RELEASE_CHECKLIST | 本版本、范围、每项状态和证据、发布批准 | 全部默认勾选或审计即部署 |
| OPERATIONS | 环境、监控、备份恢复、发布回滚、后台任务 | 生产密码、Token 和敏感日志 |

## AGENTS.md 的层级

全局规则描述个人通用习惯；项目规则描述当前产品；模块规则描述对应路径的特殊约束。按宿主实际发现规则核实，尤其子目录文件，不假设打开根目录就自动读取了全部深层规则。

用户已有全局规则只读保留。项目已有规则采用提议补充，说明作用范围和冲突。不要写“忽略全局要求”，也不要把 AGENTS.md 当成能替代权限校验、测试或审批的安全保障。

“部署前停任务”只在当前资源限制和发布流程确实需要、且用户确认后成为项目规则；必须连同任务名称、停止/恢复办法和检查项记录，避免只停不恢复。

## 开发中的更新

新想法：记录价值、场景、优先级和“未批准实施”；继续当前任务。完成一项：核对实现、验证和剩余限制再更新 TODO。新决策：写入确认日期，不能用讨论日期冒充确认日期。

旧决策发生变化时新增记录并指向被替代编号，保留历史理由，标明旧状态。小的实现细节无需全写成重大决策，避免文档噪声。

## 结束聊天前交接

1. 检查文件、差异、当前分支和未提交工作，区分用户已有改动与本次改动。
2. 按验收场景核对完成项；只做了界面、使用模拟服务、未跑真实流程的分别注明。
3. 记录实际检查命令、结果、运行环境、失败与原因；链接日志时先检查敏感信息。
4. 更新 TODO、已确认 DECISIONS、HANDOFF；文档与实际代码矛盾时标明差异，不能悄悄编圆。
5. 给新对话一个可执行的下一项任务和必要前提。写清哪些动作还没批准。

## 新对话接手

读文档 → 检查实际代码与工作区 → 复述目标、现状、阻塞、下一步 → 按原授权推进。已确认决策不重新推翻；发现过期或与代码不一致时提供证据和最小修正建议。

验收：另一个 Agent 不读旧聊天也能找到真实状态、正确命令、未解决问题和下一步；没有泄漏秘密、覆盖用户内容或把提案写成决定。
